# Фоновые таймеры арены

Фоновый обход теперь выбирает просроченные мини-игры по индексу SQLite. Индекс строится из срока текущего этапа в сохранённом JSON, поэтому формат записи и уже открытые мини-игры не меняются. При обработке кандидата заново читается его текущий этап: завершение другой мини-игры могло удалить или обновить запись. Запросы по конкретному бою по-прежнему сразу удаляют устаревшие этапы.

Рейды больше не перечитываются после проверки, если состояние не изменилось. Свежее лобби не загружается, а список участников считывается только для обновлений, которые будут переданы издателю. Проверка владельца и боевого слота остаётся. При выдаче текущей мини-игры сервер больше не копирует весь этап; внутренний ключ казино по-прежнему удаляется из публичного ответа.

## Замер

Одинаковые временные SQLite базы: 200 активных рейдов по три игрока, 200 свежих лобби, по одной открытой мини-игре на активный рейд. Ни одна мини-игра не просрочена. Медиана 30 замеров, Windows / Python 3.13, сравнение с `a07baf1`.

| Операция | До | После |
| --- | ---: | ---: |
| Фоновый поиск просроченных мини-игр рейдов | 130,27 мс | 0,01 мс |
| Весь фоновый обход рейдов с мини-играми | 294,08 мс | 125,46 мс |
| Пик временных Python-выделений на весь обход | 234 КиБ | 167 КиБ |
| Обновление записи мини-игры, без коммита транзакции | 4,8 мкс | 25,6 мкс |

Последняя строка показывает цену поддержки индекса при записи. Пик по `tracemalloc` не включает внутренние буферы SQLite и не равен общей RAM процесса. Эти числа не измеряют задержки Telegram или работу BotHost.

```powershell
.venv/Scripts/python.exe tools/benchmark_timeout_sweeps.py --baseline-ref a07baf1
```

Прошли 55 целевых тестов, включая применение индекса к старой таблице и обработку срока, не закрывающую следующий этап. Шесть сбоев отдельного прогона старых сценариев рейда, Капеллана и Китобоя воспроизводятся на `a07baf1` без оптимизации.

## Тяжёлый пересчёт мини-игр и рейтинг

При проверке столкновений явно разнесённые фигуры отбрасываются до расчёта точной геометрии. Близкие касания по-прежнему проверяются старой формулой. Координаты снаряда переиспользуются только при совпадении точного момента расчёта. Одиночная совместная защита больше не копирует данные общего поля на каждом кадре. При пропуске защиты обрабатываются только новые опасности текущей волны. Частота симуляции — те же 120 Гц, результат по-прежнему вычисляет сервер.

Рейтинг PvP выбирает одну страницу в SQLite, не превращая весь сезон в список словарей Python. Порядок прежний: рейтинг, победы, ID игрока. Своё место, калибровка, титулы и последнее имя игрока сохранены.

| Операция | До, мс | После, мс |
| --- | ---: | ---: |
| Остановка времени Аинза | 929 | 495 |
| Защитный ритуал Виктима | 523 | 267 |
| Совместная защита от трёх Плеяд | 190 | 98 |
| Стресс-сценарий: совместная защита от шести атак | 1545 | 748 |
| Своя страница рейтинга, сезон с 20 000 записями | 144,36 | 7,49 |

Замеры локальные, не на BotHost. В рейтинге пик временных выделений Python снизился с ~8 МиБ до ~8 КиБ; это не общий расход памяти процесса. Во всех шести сценариях пересчёта (12 проверок с учётом пропуска) результат совпал с `a07baf1`, включая контакты, их порядок, веса и статусы. База для замера рейтинга одноразовая, ответы старого и нового запроса совпадают.

```powershell
.venv/Scripts/python.exe tools/benchmark_qte_replay.py --repeats 7
.venv/Scripts/python.exe tools/benchmark_large_leaderboard.py
```
